実装完了(Phase 1〜2)後、**本番として動かすまでの接続・設定作業**を手順化する。上から順に実施すればクローズドβを開始できる。各手順に検証(✔)を付けているので、通ってから次へ進む。

> このドキュメントは**人間が実施する運用手順**。コードは GitHub `main`(https://github.com/biz-iterra/magical-journal)に全て入っている。

## A. NAS バックエンド(api / batch / tunnel)

NAS に SSH で入る(`ssh <ユーザー>@<NASのIP>`)。作業ディレクトリは `/volume1/docker/magical-journal`。

### A-1. 最新コードを取得(git 未インストールのため tar)

```
curl -L https://github.com/biz-iterra/magical-journal/archive/refs/heads/main.tar.gz | tar xz --strip-components=1 -C /volume1/docker/magical-journal
```

✔ `ls /volume1/docker/magical-journal/infra` に `docker-compose.yml` があること。

### A-2. `.env` を作成・記入

テンプレートを `infra/.env` にコピーして値を埋める(**リポジトリ内のファイルには書かない**。コミット事故防止)。

```
cd /volume1/docker/magical-journal/infra && cp .env.example .env && vi .env
```

記入する値(この手順書の各設置先で使う値を集約):

```env
# LINE Messaging API(Webhook 署名検証・応答)
LINE_CHANNEL_SECRET=＜Messaging API チャネルシークレット＞
LINE_CHANNEL_ACCESS_TOKEN=＜Messaging API 長期アクセストークン＞

# LINE Login(LIFF トークン検証・Flex ディープリンク)
LINE_LOGIN_CHANNEL_ID=＜LINE Login チャネル ID＞
LIFF_ID=＜LIFF ID＞

# Flex カードのキャラ画像を配信するフロントの origin(末尾スラッシュなし)
PUBLIC_ASSET_BASE_URL=https://magical-journal.＜アカウント＞.workers.dev

# Cloudflare Tunnel
CLOUDFLARE_TUNNEL_TOKEN=＜Tunnel トークン＞

# LLM(文章生成。api + batch の両方が使う: api=初回アクセス生成/登録時生成/手動再生成、batch=夜間・月次)
LLM_PROVIDER=claude          # または openai
ANTHROPIC_API_KEY=＜Claude キー＞     # LLM_PROVIDER=claude のとき
OPENAI_API_KEY=＜OpenAI キー＞        # LLM_PROVIDER=openai のとき
# CLAUDE_MODEL / OPENAI_MODEL は既定(claude-sonnet-5 / gpt-5)を使うなら未設定でよい

# 招待リスト(クローズド運用)★重要
ALLOWED_LINE_USER_IDS=＜自分の LINE ユーザー ID＞    # カンマ区切りで複数可
```

> ★ **`ALLOWED_LINE_USER_IDS` を必ず設定すること。** 本番(`NODE_ENV=production`)で空だと、セキュリティのため**全リクエストを 403 で拒否(フェイルクローズ)**する。最低でも自分の ID を入れる。招待者が増えたらカンマ区切りで追加。
>
> `GOOGLE_MAPS_API_KEY` は NAS では不要(地図・住所検索はフロント側で使うため、後述の Cloudflare 環境変数に設定する)。

保存: `vi` は `Esc` → `:wq`。**または** `vi` が不安なら次のヒアドキュメントで一括作成:
```
cat > /volume1/docker/magical-journal/infra/.env <<'EOF'
LINE_CHANNEL_SECRET=...
（上記の内容を全部貼る）
EOF
```

### A-3. ビルド & 起動

```
cd /volume1/docker/magical-journal/infra
sudo docker compose build api batch
sudo docker compose up -d api batch tunnel
```

> `sudo` はお使いのユーザーが docker グループなら不要。DB(SQLite)は Docker ボリューム `db-data` に永続化され、テーブルは api 起動時に自動作成される(マイグレーション不要)。

✔ 疎通:
```
curl -s http://localhost:3000/api/health          # {"status":"ok"}
sudo docker compose ps                              # api/batch/tunnel が Up
sudo docker compose logs --tail 20 tunnel           # "Registered tunnel connection" が出る
```

### A-4. 公開 URL の確認(トンネル経由)

ブラウザ or 別端末から:
```
curl -s https://mj-api.iterra.online/api/health     # {"status":"ok"}
```
✔ 200 が返れば NAS 公開まで完了。返らない場合は Cloudflare 側の Public Hostname 設定(Service = `http://api:3000`)と、iterra.online の DNS が Cloudflare 管理(Active)であることを確認。

## C. 外部サービス設定

### C-1. Google Cloud(Maps キーのリファラー制限)

Google Cloud Console → 認証情報 → 対象 API キー → アプリケーションの制限「HTTP リファラー」に以下を追加:
- `https://magical-journal.<アカウント>.workers.dev/*`
- (開発用)`http://localhost:5173/*`

✔ 未設定だと本番でも地図・住所検索が `RefererNotAllowedMapError` で失敗する。API 制限で「Maps JavaScript API」「Geocoding API」が有効なことも確認。

### C-2. LINE Developers

**LINE Login チャネル → LIFF**:
- 対象 LIFF アプリのエンドポイント URL = フロント公開 URL(`https://magical-journal.<アカウント>.workers.dev`)

**Messaging API チャネル**:
- Webhook URL = `https://mj-api.iterra.online/line/webhook`
- Webhook の利用 = **オン**
- あいさつメッセージ・応答メッセージ(自動応答)= **オフ**(Bot の応答と競合させない)
- 「検証(Verify)」ボタンを押して **成功(200)** になること ✔

### C-3. リッチメニューの登録

6分割リッチメニュー(docs/01 §リッチメニュー設計)を LINE に登録し、デフォルトリッチメニューとして全ユーザーに適用する。

**実行場所は開発マシン**(リポジトリ + pnpm + Node 22 以上)。NAS のコンテナには画像ファイルが入っていないため、コンテナ内では実行しない。

**必要な env**(リポジトリルートの `.env`。スクリプトが自動で読み込む。シェルで直接指定した値のほうが優先される):

| 変数 | 用途 | dry-run 時 |
|------|------|:----------:|
| `LINE_CHANNEL_ACCESS_TOKEN` | リッチメニュー API の認証(Messaging API チャネル) | 不要 |
| `LIFF_ID` | ①②⑤⑥ の LIFF ディープリンク生成 | **必要** |

**素材**: `infra/richmenu/richmenu.jpg`(2500×1686 / 1MB 以下 / JPEG。`--image <path>` で差し替え可)

```bash
# 1. まず dry-run で送信内容を確認(LINE API を一切叩かない)
pnpm richmenu:dry

# 2. 現在の登録状況を確認(任意)
pnpm richmenu:list

# 3. 本番登録(登録 → 画像アップロード → デフォルト適用 → 旧メニュー削除)
pnpm richmenu
```

`pnpm richmenu` の処理順は「①既存一覧を取得 → ②新規作成 → ③画像アップロード → ④デフォルト適用 → ⑤旧メニュー削除」。**④が成功して初めて⑤に進む**ため、途中で失敗しても旧メニューが残り「メニューが消える」状態にはならない(②〜④で失敗した場合は作りかけの新メニューだけを自動で後片付けする)。

- 差し替え(画像やアクションを変えたとき): `infra/richmenu/richmenu.jpg` を置き換えて `pnpm richmenu` を再実行するだけ。毎回新規作成 → 差し替え → 旧削除なので、何度実行しても最終状態は同じ
- 旧メニューを消さずに残したい場合: `pnpm richmenu -- --keep-old`
- 別画像を使う場合: `pnpm richmenu -- --image infra/richmenu/other.jpg`(相対パスは**リポジトリルート基準**。絶対パスも可)

**登録されるアクション**(③④のテキストは webhook ハンドラのキーワードと一致。ズレるとユニットテストが落ちる):

| # | 位置 (x, y, w, h) | 項目 | アクション |
|---|-------------------|------|-----------|
| ① | 0, 0, 834, 843 | 今日のジャーナル | LIFF `https://liff.line.me/<LIFF_ID>/` |
| ② | 834, 0, 833, 843 | 友達のタイプ診断 | LIFF `…/friend` |
| ③ | 1667, 0, 833, 843 | 今日の運勢を聞く | メッセージ送信「今日の運勢」 |
| ④ | 0, 843, 834, 843 | マイタイプ | メッセージ送信「マイタイプ」 |
| ⑤ | 834, 843, 833, 843 | 月間運勢 | LIFF `…/monthly` |
| ⑥ | 1667, 843, 833, 843 | 設定 | LIFF `…/settings` |

> 列幅の端数 1px は左列で吸収(834 + 833 + 833 = 2500)。隙間・重なりが無いことは `packages/batch/src/__tests__/richmenu.test.ts` で検証済み。

✔ 確認: LINE アプリでトークを開き直す(またはトークルームを一度閉じて再度開く)とメニューが更新される。反映されない場合はアプリを再起動する。6項目をタップして E-1〜E-6 の挙動になること。

cd /volume1/docker/magical-journal/infra

## F. 友達診断の「AI占い」144 通りの事前生成

友達診断の AI占いは **API を叩かず、事前生成した静的 JSON を読むだけ**にしている(理由と slug 規則は docs/12「性質レポートの静的配信」)。**この生成を実行するまでは、友達診断の AI占いは常に「準備中」表示になる**(他の診断表示は正常に動く)。

**実行場所は開発マシン**(リポジトリ + pnpm + Node 22 以上)。生成物はフロントのリポジトリ内 `packages/liff/public/personality/` に書き出されるため、NAS のコンテナでは実行しない。

**必要な env**(リポジトリルートの `.env`。スクリプトが自動で読み込む。シェルで直接指定した値のほうが優先される。**キーはコード・ログに出さない**):

| 変数 | 用途 | dry-run 時 |
|------|------|:----------:|
| `LLM_PROVIDER` | `claude` / `openai` / `mock`(既定 `claude`) | 不要 |
| `ANTHROPIC_API_KEY` | `claude` 使用時 | 不要 |
| `OPENAI_API_KEY` | `openai` 使用時 | 不要 |
| `CLAUDE_MODEL` / `OPENAI_MODEL` / `LLM_MAX_TOKENS` | 任意(未設定なら既定) | 不要 |

```bash
# 1. dry-run: 何件・どのファイルを書くかの確認のみ(LLM を一切呼ばない・キー不要)
pnpm personality:static:dry

# 2. 文章品質の確認: まず 1 件だけ生成して中身を読む
pnpm personality:static --limit 1
#    → packages/liff/public/personality/ir-plus-aquarius.json を開いて文言を確認

# 3. 本番生成: 未生成分だけを順に生成する(144 通り)
pnpm personality:static

# 4. 文言を作り直したいとき: 既存ファイルも上書きする
pnpm personality:static --force
```

- **所要時間・コスト**: 1 件あたり LLM 1 回。逐次実行のため **144 件で目安 10〜25 分**(モデル・混雑による)。トークンは 1 件あたり入力数百・出力 500 前後。
- **中断・再開**: 既に存在するファイルは自動でスキップする。途中で止めても **同じコマンドを再実行すれば続きから**進む(スキップは LLM を呼ばないので追加コストなし)。
- **失敗の扱い**: 1 件失敗しても止めずに続行し、最後に失敗一覧をログに出す(終了コードは 1)。**再実行すれば失敗分だけが再試行される**。
- **出力先**: `packages/liff/public/personality/<タイプ slug>-<星座>.json`(例 `il-plus-taurus.json`)。`--out <dir>` で変更可(相対パスはリポジトリルート基準)。
- **★生成後は必ず 144 ファイルをコミットしてフロントを再デプロイする**(B-2)。生成物はフロントの静的アセット(`packages/liff/public/`)で、ビルドはリポジトリの内容から行われる。**コミット + 再デプロイするまで本番では配信されず「準備中」のまま**。

✔ 確認: `packages/liff/public/personality/` に **144 ファイル**あること(`ls packages/liff/public/personality | wc -l`)。
✔ 再デプロイ後、`https://<フロントの公開 URL>/personality/il-plus-taurus.json` が JSON として開けること。
✔ LIFF の友達診断で任意の生年月日を診断 →「AI占い」→ 6項目(基本的な性質/仕事上の強み/弱み/人付き合いの傾向/得意なこと/苦手なこと)が表示されること。
